# Architecture: why not just check the service call's context id?

Home Assistant's state-changed events carry a `context.id`, and a common
pattern for "did my own automation cause this" is to compare a new event's
`context.parent_id` against the context of the service call an automation
just made. For this specific problem — a cover automation trying to tell
its own moves apart from a human's — that pattern is not reliable enough.

## The async-confirmation problem

When `sun-based-auto-close.yaml` calls `cover.set_cover_position`, that
service call has a context id, and the resulting `state_changed` event for
the *position being set* often does chain back to it correctly. But covers
report their *final resting position* — the number you actually see in the
UI once the motor stops — as a separate, later state update, generated by
the device/integration itself once it polls or receives the physical
confirmation. That second event is not guaranteed to carry a
`context.parent_id` pointing back to the original service call; depending on
the integration, it can arrive with a fresh context of its own, or with a
context tied to a polling update rather than the triggering service call.

In practice this means: a "was this context caused by my automation"
check works most of the time, then silently stops working for exactly the
event you actually care about — the final position — with no obvious error,
just an automation that occasionally can't tell the difference between its
own action finishing and a human adjusting the cover a few seconds later.
That's a bad failure mode: it's rare enough to pass casual testing, and
common enough to eventually cause the automation to either fight a manual
adjustment, or mistake its own reopen for a manual override and refuse to
act again until the next day.

## The fix: compare timestamps, not contexts

Every automation in this repo that moves a cover on purpose writes the
current time into that cover's `last_auto_action_helper`
(`input_number.set_value`, right after the `cover.set_cover_position` call).
`manual-override-detect.yaml` then triggers on the cover's position
changing and asks a much simpler, much more robust question: *when did
this change happen, relative to the last time our own automation acted on
this specific cover?*

- If the gap is small (within a short debounce window, 2 minutes by
  default), it's almost certainly this repo's own action finishing —
  ignore it.
- If the gap is large, or there's no record of this automation having
  acted on this cover *today* at all, it must have been a human — set the
  cover's `override_helper`, so the sun-based automation leaves it alone
  for the rest of the day.

This sidesteps the whole context-chain reliability question: it doesn't
matter whether the final-position event's context links back correctly or
not, because the comparison never looks at context at all. It only cares
about *when* things happened, which every state-changed event reports
accurately regardless of how its context id was assigned.

## Trade-offs

- The debounce window is a real trade-off: too short, and a slow-moving
  cover's own final-position event can arrive after the window closes,
  getting misread as manual. Too long, and a genuine quick manual
  adjustment right after an automated move gets missed. 2 minutes is a
  reasonable default for typical motorized blinds; widen it if your covers
  are slow, or your integration's polling interval is long.
- This approach assumes only this repo's automations, or a human, ever
  move these covers — if you have a third system (e.g. another automation,
  a scene, a different integration) also moving them, it needs to write to
  the same `last_auto_action_helper` too, or it will be misidentified as a
  manual override.
